## M02 EERM 方法身份与 IRM 适用性 —— 成立

`configs/week11.yaml:86-97`：

```yaml
irm:
  enabled_for: [T2_PH]
  warmup_epochs: 50
  require_two_classes_per_env: true
eerm:
  enabled_for: [T1_Nordic, T2_PH, T2_ON, T3_DiagnoseFrance]
  K_values: [2, 4]
  embedding_for_clustering: frozen_heco
```

两处问题：

1. **方法身份**。本文实现是"冻结 HeCo 嵌入上 K-means 生成固定虚拟环境 + IRMv1 惩罚"。Wu 等 ICLR 2022 的 EERM 原方法含**对抗式图编辑器**与**跨环境风险方差**目标，不是固定聚类。以本文实现的结果断言"EERM 失败"属方法身份错误。
2. **IRM 不可用的理由**。"源域环境单类导致 risk 梯度无法定义"在数学上不成立——交叉熵及其对可训练标量 w 的梯度在单类环境下照常有定义。真正的约束是：单类环境下"环境内最优分类器"不可识别，IRM 的不变性约束退化为空约束；且本实现显式设置了 `require_two_classes_per_env: true` 这一**实现层门限**。二者应分开陈述。

另有两处内部矛盾：正文称 T2_ON 与 T2_PH 同源池，却又称仅 T2_PH 结构上可行；附录写"虚拟环境由 finetune embedding 上的 K-means 聚类生成"，与配置的 `frozen_heco` 不符。

**处置**：全文将该实现改称"K-means 虚拟环境的 IRM 代理基线（EERM-proxy）"并列出与原 EERM 的差异；IRM 的不可用理由改写为不可识别性 + 实现门限；附录嵌入来源改为 frozen_heco；T2_ON 未运行 IRM 的原因改为按配置 `enabled_for` 限定，标注为"本实现未评估"而非性能判断。

## M03 StruRW 训练描述与验证隔离 —— 成立

`src/train/train_transfer.py:698-706`：

```python
def build_source_label_inputs(bundle, split_frame):
    source_frame = split_frame[split_frame["domain_role"] == "source"]   # 含 source_val
    for _, row in source_frame.iterrows():
        labels[int(row["graph_node_index"])] = int(row["label"])
```

该标签向量供 StruRW 的 CSBM 块间连接概率估计使用，因此**源验证集标签进入了结构权重的拟合步骤**，不再是纯粹的独立选择集。这不是目标域测试标签泄漏，但必须披露。

训练预算也不一致：`configs/week7_transfer.yaml` 中 `finetune.min_epochs_before_early_stop: 50`（source_only/StruRW）、`dann.min_epochs_before_early_stop: 80`、StruRW final 阶段 `final_force_full_epochs: true` 且 `final_min_epochs_before_early_stop: 200`。同时 `pseudo_label_iterations: 2` 与 `pseudo_labeler_*` 系列参数表明伪标签器仍是分阶段拟合，与正文"后期改为单阶段"不符。

**处置**：3.3.3 补写源验证标签的使用范围与各臂训练预算差异，撤回"已隔离的公平对比"含义；把"改为单阶段"更正为"最终分类器改为单阶段，伪标签器仍为 2 轮迭代拟合"。
